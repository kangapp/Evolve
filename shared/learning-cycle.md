# 反例到小型检查的工作循环

第二次任务发现过时经验、输入域变化、重复失败，或准备把经验变成检查时读取。字段、来源时序与状态规则只维护在[项目学习请求](protocol.md#project-learning)；规则正文的具体批准与实际应用按[规则交付](knowledge-rules.md)处理。

## 先核对原经验的实际范围

恢复当前正式知识、工作方案与少量经验，读取真实来源和本次输入。旧列表样例通过只能证明原观察，不能替代新迭代器、空值或其他输入域的验收。明确保存命中、采用／拒绝及理由；新决定用 influence 说明实际影响的方案、任务、检查或 AC，列出 affected_items；尚未产生同定义的后续实际结果时，效果保持 unknown。

保留事实与适用性两个层次：发现新反例不改写原观察成错误，也不把旧绿灯当新支持。反例用真实决定及其后的同一 Task 定义结果关联；来自另一 REV、另一 Task 或决定之前的结果不能移作该次采用效果。

## 传播影响，保留正式字节

反例保存后，重新读取原经验当前状态、关联规则和未执行方案的 learning_context。来源待复审时，不再当可靠建议；旧采用、原版本、正式批准和历史验收仍保留。未执行方案须能看到 state_changed_since_decision；需要更新方案时交 propose，不能靠一次 resume 自动实施。

规则原文仍在不表示其来源当前可用；实际目标验收可以因来源待复审而 blocked。Learn 不自动改正文或沿旧批准重绑新依据。若本轮没有具体批准规则修订，保留字节并报告待复审，只阻碍真实依赖项。经验可选，不因为它待复审就全局禁止独立核查和已有范围内的工作。

## 先查现有检查，再做最小改进

机械问题先确认现有 lint／测试是否缺失、未执行、配置失效或漏了本次输入。真实运行原检查和独立反例，保留“原检查绿、实际缺口仍在”等未改善事实。不能删原断言、用当前实现计算预期，或把所有失败都改成成功退出。

提出最小、可独立验证的检查变化。若还要修源码，在完整方案中分清“检查能捕捉错误”与“当前源码通过检查”两项成果；先完成检查的实际 Task 验收，再推进所需后继。可使用受控错误／正确样例证明检查确实区分目标行为，限制于实际观察范围；这种检查验证通过不等于仍有错误的当前源码已通过。

检查文件、CI、hook 和业务源码由普通 Change／apply／verify 处理，Learn 只提出改进和记录学习。按具体文件与原检查准备当前授权，扩大范围先呈现准确新方案。没有必要不另建框架、生成器或通用规则执行器。

## 记录效果，不能由整单成功代填

实施后按原判据验收，并保留错误变体仍红、正确行为变绿的实际材料。针对某一检查 Task 的采用效果，用该 Task 定义下、采用之后的真实 apply／verify 来源；整项 VER 不能冒充另一个 Task 的证据。REV 改变定义后，先记录新的真实采用，不转移旧反馈。

用 learning_context.consumption 核对实际采用及待反馈项，分别说明哪些建议被采用、哪些无帮助、哪些尚无法归因；同一决定的结果不能覆盖。helped 仍是有界观察者评估，不自动 active 或批准正式规则。没有新发现也须实际检查后再记 no_new_learning；未检查保持 pending。

最后恢复尚未执行的相关方案，报告经验、规则来源或检查上下文的变化及下一步。保留其未执行状态，不用其他工作完成替它记 done。资料故障、未覆盖和真实无命中仍按查询结果区分，必要时回查实际原文。
