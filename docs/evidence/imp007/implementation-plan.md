## 第 2 项的落地边界

在开放正式写入前，以现有 `init.baseline.apply` 的 journal／claim／artifact／recover 协议为依据，增加 sync owner 的应用路径，不另建文件写入器。每次应用必须引用准确候选版本、实际批准事件与最新内容检查；只读查询不能代替这些来源核查。候选通过、批准、文件应用、应用后验证四种事实独立保存。

- 持久资料：增加 delta 的稳定身份、目标及前继，以及 `spec_applications` 的批准提案版本、实际前后摘要、artifact 版本、operation 和验证引用；唯一应用身份绑定 delta 与实际目标内容摘要，不随 REV 重新分配 ADD。
- 必需文档：方案先声明负责动作、正式文件和对应 AC；owner 应用登记 Task 的真实产物，`verify` 重新读取已应用的实际目标再判断完成。普通 `apply` 仍拒绝正式文档。未应用／未复验、最新失败或外部漂移均阻止封存；附带候选允许保留待审。
- 兼容边界：必需文档任务条件或新表开放前升协议；用已保留的完整 alpha.7／alpha.6 写入器验证明确拒绝，禁止静默降级或迁移。
- 中断：在登记后、文件提交后和数据库事实提交后实际终止进程；恢复引用原批准和原 journal，只核实／补齐确定事实，不重跑内容检查，不把第三方字节回滚。
- 分步验证：先以单候选完整路径及失败／中断分支验证第 2 项，再接第 3 项的同批同文件证明链；每项保留独立完整包，不把前项通过当作后项验收。

这里明确下一子流程的实现与验证范围；接口和持久字段以最终代码及实际验证记录为准，尚未开放的路径继续明确返回 unavailable。
