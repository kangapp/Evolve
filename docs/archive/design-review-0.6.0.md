# 0.6.0 严格审核与 0.6.1 修订

日期：2026-10-31（Asia/Shanghai）。用户要求按已确认实际需求严格审核，发现问题直接修订，暂不开始插件编码。本次对象为五份 0.6.0 主文档、入口、图册及文档检查器；修订基线为 **0.6.1**。

## 结论与审核边界

现有方向符合需求：单项目积累、按复杂度推进、正式知识集中确认、按影响验证、多任务并存及授权数据修改。问题主要在交叉场景：正式文档作为必需成果、正常换会话、同方案失败修复、知识提案跨任务演进，以及维护和真实写入的竞争。

共修订 **12 项：严重 3 项、中等 7 项、一般 2 项**。以下是设计契约缺口及文档工具缺陷，不是已经复现的插件运行故障。状态均为“设计／文档已修订”；产品行为仍需未来实现和验收。

保持八个 Skill、十四动作、Markdown＋SQLite、现有领域对象和单项目范围。没有增加平台、后台调度器、个人库或部署能力；移除冗余 init profile，以既有 run／operation／提案字段表达所需差异。

## 严重

### DR-060-S1：正式知识作为交付物时，封存条件与应用前置不闭合

**原依据**：workflows 的 archive／sync 允许知识待审时封存，sync 又要求验证；verify 没区分候选与实际目标。design 将正式文档列为成果，但未给独立闭环。

**反例**：用户要求修正正式指标文档。候选已经检查通过、尚未批准或写入；系统可能以“知识可延期”为由归档，或为了满足 sync 的“已验证”条件要求目标文件先被修改，形成循环。

**修订**：明确 required 与 followup。只有附带知识可以待审；纯知识任务按候选检查、具体批准、init／sync／learn 应用、实际目标核查、封存推进。Task 指明负责动作，Verification 区分 candidate／applied；不让 apply 越权写正式文件，也不额外加一套工作流对象。

**验收**：V-111／V-112；候选通过不证明实际文档已更新。见 [封存](../workflows.md#archive)、[知识持久化](../runtime.md#knowledge)、案例 M。

### DR-060-S2：备份与换库只描述结果保护，缺少在途执行隔离与一致采集步骤

**原依据**：runtime recovery 要求全局换库暂停写入、切换 epoch，但未明确如何阻止已通过旧检查的执行者继续写文件／发外部请求；一致恢复包也缺少库与多文件的共同采集依据。

**反例**：A 已检查旧 epoch，B 恢复旧库后 A 才派发补数；或者先备份库，随后文件被修改，再把当前文件复制入包，得到每个摘要都正确但整体不一致的包。

**修订**：既有独立 control journal 建维护屏障，与实际派发准入协调；排空仍能写／派发的本地实例后才能换库，旧 generation／epoch 拒绝。已发送未知效果保留保护。备份固定检查点与不可变引用集合；未登记实际字节单列保护附录，未解决 journal 不能标一致包。宿主不支持排空时拒绝在线 restore。

**验收**：V-113／V-114；按真实竞争次序和故障点验证，不只检查字段。见 [恢复](../runtime.md#recovery)、案例 P。

### DR-060-S3：批准可能只绑定入口，取消或失败也未充分区分已发出的效果

**原依据**：runtime external-effects 绑定脚本／argv／参数，但未规定间接 SQL／辅助脚本、连接别名实际解析和取消后的部分效果；maintain cancel 只保存任务事实。

**反例**：批准的 shell 入口没变，被其读取的 SQL 或连接别名已变；另一条操作发送后被取消，外部仍可能完成部分写入。若只看入口摘要或取消／failed 标签，可能执行未批准内容或重发已产生效果的部分。

**修订**：绑定实际执行清单与真实目标，固定候选字节或派发前核对全部声明依赖；无法确定范围时不放行。取消只阻止后续派发，unknown 和部分效果保持占用与核实，重试／补偿按剩余真实范围另核授权。

**验收**：V-115／V-116；入口不变的依赖替换、派发后取消、部分失败均须覆盖。见 [外部操作](../runtime.md#external-effects)、案例 Q。

## 中等

### DR-060-M1：正常暂停缺少收尾，容易把跨会话变成异常恢复

**原依据**：run 只写终态与异常 recover；续接要求核实 started 拥有者，claim 使用进程信息但没有正常轮次释放规则。

**反例**：用户正常换会话，原宿主仍开着，旧 run 和 claim 可能长期占用；每次继续都要求判断异常或执行 recover。

**修订**：安全点保存 partial 结果、剩余工作及授权，正常 finish 并释放已结束的本地写段。run 不等于宿主进程；claim 绑定具体执行实例／generation。外部未知独立保留，新会话直接沿封存结果续接。

**验收**：V-117。见 [续接](../workflows.md#routing)、[执行生命周期](../runtime.md#execution)、案例 N。

### DR-060-M2：同 REV 的验收失败没有明确任务重开路径

**原依据**：states 明确“定义变化转 todo”，apply 要求失败后修正，但未说明定义不变时谁重开已 done 任务。

**反例**：单项检查通过后任务 done，集成失败证明原 AC 未满足；实现可能强造 REV、改测试标准或保持 done 无法继续。

**修订**：已有修改授权下，由实施负责者引用失败证据重开受影响任务，保持原 REV 和旧事实。环境问题只阻碍验收；仅 verify 不改实施状态。

**验收**：V-118。见 [实施](../workflows.md#apply)、[状态](../workflows.md#states)、案例 N。

### DR-060-M3：集中确认后，同文件基线推进与旧延期提案缺少处理规则

**原依据**：批准绑定完整基线，基线变化需重新确认；同时承诺整批批准不逐文件重复确认，但没有同批应用证明或跨任务替代的具体处理。

**反例**：同一文件两项都批准，第一项写入后第二项因摘要不符重复询问；或者 A 的旧延期提案后来覆盖 B 的新行为。

**修订**：确定同文件顺序、冲突和批准范围，仅对可证明由同批批准应用造成的非语义变化复用批准链；实质变化暂停。提案版本及 supersedes 可追溯，旧批准不转移，旧已应用事实不删除。

**验收**：V-119／V-120。见 [集中审阅](../workflows.md#knowledge-approval)、[知识协议](../runtime.md#knowledge)、案例 O。

### DR-060-M4：检索失败和空结果未分开，归档后的上下文可能失去可发现性

**原依据**：有按需检索、只读索引失配报告，却未确定读取原文的降级路径，也未保证已归档成果及未应用提案参与检索。

**反例**：索引坏了被当成“没有项目经验”，又让用户完整补背景；已验收但知识延期的事实在下次任务中消失。

**修订**：区分可用、未覆盖、索引失配、不可访问；纯读回查原文／已知引用，仍不足时才询问。检索包含相关归档结果、延期差异和反例，明确各自权威。可选经验不可用不全局阻断，必需依据缺失限制相关动作。

**验收**：V-121。见 [上下文](../runtime.md#documents)、案例 R。

### DR-060-M5：测试通过到完成声明之间，缺少统一的最终依据核对

**原依据**：fingerprints 检查执行前后现场，archive 要求当前通过，但没有明确消费旧 VER 时重算当前前置和最新结果的截点。

**反例**：测试后、封存前修改代码，数据库仍保存 passed；或者新的同范围失败出现，较早通过被采用。归档后再变化，也可能继续显示“当前通过”。

**修订**：汇报当前通过、sync 使用实现证据和封存前统一重核当前 REV／AC、相关现场、检查配置、依赖及最新适用结果；封存保留明确截点，历史完成与当前适用性分开。只重核相关范围，不引入全项目持续监控。

**验收**：V-122。见 [证据时效](../runtime.md#fingerprints)、案例 R。

### DR-060-M6：verify 的“补必要测试”与只验收授权、职责边界冲突

**原依据**：verify 段落要求补测试，同时又声明不静默修改业务实现；没有明确测试源码和持久夹具由谁修改。

**反例**：用户仅请求验收，Agent 直接新增测试源码、改脚本或改配置，以便完成检查。

**修订**：verify 报缺口，apply 在修改授权内补测后返回 verify；完整实现测试请求不重复批准。隔离检查本来允许的临时输出仍可产生并记录，不把它等同于业务源码编辑。

**验收**：V-123。见 [验证](../workflows.md#verify)、案例 N。

### DR-060-M7：早期学习只有消费入口，阶段完成也可能把“有结论”当通过

**原依据**：M1 明确最小经验检索，演练允许“引用既有事实或经验”；首版完成条件为“全部有效 V 有结论”。

**反例**：用预置经验即可宣称学习链路打通；failed／blocked 虽然有结论，也被算阶段或首版完成。

**修订**：M1 必须真实产生候选及来源，再在新会话检索／核实／采用或拒绝并反馈。必需断言通过才可完成对应阶段；受限版本可以交付，但不得称完整首版。V 按七组能力复用场景执行，不一条编号建一套流程。

**验收**：V-124，以及 [里程碑完成条件](../delivery.md#milestones)和[效果演练](../delivery.md#evaluation)。

## 一般

### DR-060-G1：初始化仍保留两种已无独立行为的 profile

**原依据**：0.6.0 已把业务骨架移出 init，但仍保留 records_only／development，且与梳理深度分开。

**影响**：增加用户理解、状态覆盖和实现分支，实际两者均是记录接入、发现资料和提出候选。

**修订**：统一增量 init，记录实际覆盖与缺口。原 V-054 保留编号但更新判据；无 profile 迁移或新初始化状态，不影响按需梳理。

**验收**：V-125。见 [init](../workflows.md#init)、图 04。

### DR-060-G2：图册检查能通过未重新生成的旧 SVG

**原依据**：check_design.py 检查 manifest、存在性、尺寸、引用及文本边界，但没有校验当前图源／渲染器与 SVG 的对应关系。

**反例**：改图源中的授权条件、不重新生成；旧 SVG、旧 manifest 仍然互相吻合，检查通过。

**修订**：manifest 增加每图源内容、渲染器和实际 SVG 摘要，检查器核对对应关系与正文编号引用；保留语法和边界检查。版本常量集中，历史快照逐个校验。

**验证**：文档工具可现在验证；在隔离副本中故意改图源、改 SVG 或引用未定义 V，应分别失败。此检查不能证明业务语义正确，不新增一个“插件功能已通过”的 V。

## 已确认需求与复杂度控制

- 四类工作共用对象和流程，正式文档作为成果的缺口已补；部署与个人库仍退出。
- 简单任务短方案、复杂任务 spec／任务清单及整体确认保持；测试职责不扩大修改授权。
- 上下文积累补可发现性与检索降级，正常换会话不走异常恢复仪式。
- 正式知识确认保持，附带延期不妨碍已完成成果，必需交付物不被延期规则豁免。
- 多任务以相关写段协调，局部失败不阻断全项目；换库仍必须维护屏障，不把并发保护写成后台调度系统。
- 实际数据写入保持单次具体授权和核实，不以通用脚本入口规避范围。
- 新增字段复用 Task／Verification／knowledge_proposals／resource_claims；没有新增领域实体或业务状态机。候选检查与应用后检查可有等价证明，避免机械重跑。
- 本轮增加 15 个反例断言 V-111—V-125 和案例 M—R；历史编号不重排，执行按代表场景聚合，不要求 125 个独立测试流程。
